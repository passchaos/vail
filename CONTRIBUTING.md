# Contributing

## Setup

1. Install Zig `0.16.x`.
2. Clone the sibling `vort` package next to this repository so that
   `../vort` resolves.
3. Run `zig build test-all` and `zig build check` before making changes.

## Workflow

- Keep changes focused and preserve unrelated worktree changes.
- Run the smallest relevant test first, then `zig build test-all` for changes
  that touch public APIs, module boundaries, or shared code.
- Run `zig build check` before committing.
- For performance changes, record the methodology and results as described in
  [`docs/benchmarks.md`](docs/benchmarks.md).

## Module boundaries

The intended dependency direction is `crypto <- x509 <- tls <- quic`.

- `crypto` must not import `x509` or `tls`.
- `x509` must not import `tls`.
- Use the owning module's public entry point (`crypto/mod.zig`,
  `x509/mod.zig`, `tls/mod.zig`, `quic/mod.zig`) instead of reaching into
  another layer's internal files.
- Test-only imports belong inside test blocks and must not become production
  dependencies.

See [`docs/architecture.md`](docs/architecture.md) for details.

## Tests

- Put unit tests next to the implementation they exercise.
- Use module-level `tests.zig` files for cross-file behavior within a layer.
- Use `test/` for package-level and cross-module integration tests.
- Prefer deterministic vectors and interoperability oracles over
  implementation-specific expectations.
- Add a regression test for every bug fix.

## Formatting

- Run `zig build fmt` before committing.
- `zig build check` runs `zig fmt --check` and `test-all`.
- Generated tables are excluded from formatting. Do not hand-edit them; update
  the generator in `tools/` and regenerate.
- Update `tools/generated_manifest.txt` when a generated file intentionally
  changes, then run `zig build check-generated`.

## Generated code and assembly

- Generated tables must carry a `Generated by tools/...` header.
- Embedded `.S` files must carry SPDX headers and a pinned upstream revision.
- Keep vendored assembly separate from the Zig ABI wrapper.
- Re-run fixed-vector, differential, and interoperability tests after updating
  third-party code.

## Security-sensitive changes

Changes to secret-dependent code, constant-time behavior, zeroization, key
parsing, certificate verification, or record protection require targeted
review. Add evidence under `docs/evidence/` when the change involves a subtle
compiler, platform, or timing question.

Do not report suspected vulnerabilities in a public issue; see
[`SECURITY.md`](SECURITY.md).
